## Course landing

### Title
和 AI 一起做資安：從「看起來安全」到「有證據知道哪裡還不安全」

### Intro
你不需要先背漏洞清單，也不用先學一整套攻擊工具。

這門課會反覆問八個問題：

1. 什麼事情不能發生？
2. 什麼可能讓它發生？現在多值得先處理？
3. 跨過這條線後，哪些東西不能直接相信？
4. 這份資料到了下一站，會被當成什麼？
5. 如果一個元件已經失守，還能走多遠？
6. 資料、Secret、套件和部署產物要怎麼信任？
7. AI 說修好了，我們憑什麼相信？
8. 真的出事後，怎麼限制影響並恢復？

AI Agent 會幫你整理、追蹤、提出可能問題、執行工具和產生測試。你要學的是怎麼用系統行為與證據判斷它的答案。

## Unit 1｜什麼不能發生？

### Opening
文件功能都正常。

Alice 可以開自己的私人文件，也能分享給 Bob。

現在問一個不同的問題：

> 哪些結果一旦發生，你會認為這個系統的保護失敗了？

### Observe
切換「陌生人讀取」「viewer 修改」「服務中斷」，看哪個東西發生變化。

### Reveal
先找需要保護的東西。

**Asset（資產）**：如果它被看到、改掉、拿走或不能使用，會造成影響的資料、服務、身分或能力。

### CIA
看到的損害可以用三種常見語言描述：

- **Confidentiality（機密性）**：不該看到的人看到了。
- **Integrity（完整性）**：不該改的人改了，或狀態變得不正確。
- **Availability（可用性）**：需要使用的人在需要時不能使用。

一個事件可能同時影響不只一項。

### Scope
把文件從「私人」改成「公開」。

陌生人現在能讀到它，還算資料外洩嗎？

保護要求需要 scope。

### Summary
先問：

> 我在保護什麼？什麼結果不能接受？這個要求在哪些條件下成立？

再談 MFA、WAF、加密或其他解法。

## Unit 2｜有漏洞，就一定要先修嗎？

### Opening
Service A 和 B 都被掃到同一個高嚴重度漏洞。

你只有時間先處理一個。

只看分數夠嗎？

### Observe
打開「版本」「能不能從外部碰到」「是否已有實際利用訊號」「會影響什麼資料」四份 evidence。

### Terms
**Vulnerability（漏洞）**：可以被利用、讓安全要求失效的具體弱點。

**Threat（威脅）**：可能造成傷害的事件、情境或行動者。

**Risk（風險）**：這件事發生的可能性與發生後影響，在目前情境下合起來看。

### EPSS
EPSS 回答的是：

> 這個公開 CVE 在接下來 30 天被觀察到實際利用活動的機率估計。

它不知道你的 server 有沒有這個版本，也不知道你的資料有多重要。

### KEV
KEV 告訴你：

> 這個漏洞已經有確認的實際利用紀錄。

它也不是「catalog 外就安全」。

### Summary
漏洞資訊是 evidence。

最後仍要回到：

> 我真的受影響嗎？攻擊路徑碰得到嗎？後果是什麼？現在有什麼 mitigation？

## Unit 3｜登入成功，為什麼還不能直接相信？

### Opening
Alice 已經登入。

她把 URL 裡的文件 ID 從自己的 42 改成 Bob 的 73。

伺服器現在知道她是 Alice。

這足夠決定她能不能讀文件 73 嗎？

### Terms
**Authentication（身分驗證）**：確認「你是誰」。

**Authorization（授權）**：決定「你能不能對這個東西做這件事」。

### Observe
把權限檢查從「讀資料之前」移到「資料回傳之後」。

HTTP 最後仍然可以顯示拒絕，但資料已經離開 server。

### Trust boundary
**Trust boundary（信任邊界）**：

> 資料或要求跨到這裡後，接收端需要重新判斷哪些東西可以相信。

### Least privilege
Worker 只需要讀 thumbnail source。

為什麼它也能刪掉整個 bucket？

**Least Privilege（最小權限）**：只給完成工作真正需要的權限。

### Summary
每個 access 都問：

> 誰？要操作什麼？做什麼？為什麼允許？真正能阻止它的地方在哪？

## Unit 4｜這串文字到了下一站，會被當成什麼？

### Opening
同一串外部文字可以進：

搜尋條件、商品評論、檔案路徑、背景處理工作。

文字沒有變。

解讀它的東西變了。

### Observe
把資料分別送進 SQL、HTML、Path 與模擬的 process API。

看它是「資料」，還是開始改變 query structure、markup、destination 或 operation。

### Validation
**Input Validation（輸入驗證）**：

> 檢查這份資料是不是我們的業務真的接受的型別、範圍和格式。

它很重要，但不是所有 injection 的完整答案。

### Parameterization
搜尋資料不應自己變成 SQL structure。

**Parameterization（參數化）**：先固定 query structure，再把外部值當資料傳進去。

### Context
SQL 的保護不會自動保護 HTML。

每個 interpretation context 都要問自己的安全建構方式。

### Summary
不要只問「有沒有 sanitize」。

問：

> 這份資料下一站會被當成什麼？它能不能改變原本的結構或目的地？

## Unit 5｜先假設 API 已經失守

### Opening
這一章不問「怎麼防止 API 被攻破」。

先假設：

> API 現在已經不可信。

按下 Run，看它能沿著現有 credential、permission 和 network route 碰到哪裡。

### Blast radius
**Blast Radius（影響範圍）**：

> 從這個已失守的位置出發，在目前條件下還能影響哪些資源。

### Least privilege revisit
把 API 的 database credential 從 admin 改成只讀。

攻擊起點沒消失。

能做的事情變少了。

### Segmentation
**Segmentation（分段／隔離）**：限制不同系統區域之間可以直接建立哪些連線。

它不能取代資料庫自己的權限，但可以少掉一條攻擊路徑。

### Summary
安全設計也要問：

> 如果第一層真的失敗，下一層還剩下什麼保護？

## Unit 6｜「有加密」到底保護了哪一種情況？

### Opening
資料庫磁碟有加密。

把 threat 切成：

- 硬碟被拿走
- Application 已經被控制

看結果有沒有一樣。

### Reveal
加密放在哪一層，決定它能擋住哪一種 threat。

### Minimize
最少需要保存的敏感資料，就是最少需要保護的敏感資料。

**Data Minimization（資料最小化）**：只保存完成目的真正需要的敏感資料。

### Secrets
CI token 已經出現在公開 log。

把它從設定檔刪掉。

它現在失效了嗎？

不一定。

**Revocation（撤銷）**：讓舊 credential 不能再使用。

**Rotation（輪替）**：建立 replacement credential，並把使用者／服務切換過去。

### Supply chain
程式從 source code 一路經過 dependency、CI、artifact 到 deployment。

任何能替換其中一段的人，都可能改變最後執行的東西。

### Summary
信任不只存在 request path。

也存在：

> 資料從哪裡來？Secret 誰能拿？Dependency 從哪裡來？真正部署的是哪一份 artifact？

## Unit 7｜AI 說修好了，我們憑什麼相信？

### Opening
AI review 說：

> 這裡可能有安全問題。

Semgrep 出現一個 finding。

Security test 是綠色。

這三件事代表同一件事嗎？

### Evidence surface
打開不同 evidence source，看每一個能看到什麼。

### Semgrep
**SAST（靜態應用程式安全測試）**：在不靠 production 攻擊操作的情況下分析程式碼，尋找符合安全規則或資料流條件的問題。

Semgrep 的基本循環：

> rule → match → finding → 調查 → 修正 → 再掃一次

**Finding** 是「工具找到一個符合分析條件的地方」。

它需要調查。

### FP / FN
工具標到了，但不是我們要找的問題：

**False Positive（誤報）**。

真的有問題，但工具沒有找到：

**False Negative（漏報）**。

### Tests
安全測試回答的是特定行為。

例如：

> Alice 嘗試修改 Bob 的文件時，系統拒絕，而且資料沒有改變。

這比「403」多驗證了一個 side effect。

### Runtime
上線後還需要 evidence。

安全 log 至少要讓調查能回答：

> 什麼時候？在哪裡？誰？做了什麼？

不要把 password、token 或不必要的敏感內容一起寫進去。

### Summary
每次看到 AI 或工具的結論，都問：

> 它看了什麼？它能證明什麼？它看不到什麼？

## Unit 8｜真的出事了，現在先做什麼？

### Opening
Deployment credential 被偷了。

系統出現一筆不熟悉的 deployment，接著有大量資料讀取。

現在有一個 alert。

第一件事不是猜完整故事。

先分：

> 我們已經知道什麼？還不知道什麼？什麼傷害可能還在繼續？

### Containment
**Containment（限制影響）**：

> 先讓 incident 不要繼續往外擴大。

試著 revoke credential、隔離 service、縮小 permission。

每個動作都可能有 operational consequence。

### Recovery
把 code rollback 了。

被改過的資料會自動恢復嗎？

不會。

把 backup restore 了。

被偷的 credential 會自動失效嗎？

也不會。

**Recovery（恢復）**：重新建立一個可接受、而且有證據支持的可信運作狀態。

### Close the loop
最後把 incident 帶回：

- threat model
- permission
- security test
- scanner / review
- logging / alert
- response procedure

### Summary
Incident response 最後仍回到同一個問題：

> 我們憑什麼知道現在已經安全到可以恢復運作？

## Final

你會拿到一個完整 SaaS 系統。

不會告訴你這題屬於哪一章。

你可以和 AI Agent 一起分析，也可以使用課程提供的 evidence tools。

最後你需要說明：

- 你在保護什麼；
- 哪些 trust assumptions 最重要；
- 哪些 control 放在哪裡；
- 如果一層失守，影響能走多遠；
- 你用什麼 evidence 驗證；
- 出事時怎麼發現、限制與恢復；
- 還有哪些事情你不知道。

接著再把同一套方法帶到一個你熟悉的系統。

### U1／1：先觀察，再描述損害

文件內容與服務都是需要保護的東西。被讀取、被改動與不能使用是不同結果；先問誰原本應該有權限，再判斷是否違反要求。

例如公開文件被陌生人讀取符合分享政策；同一人修改文件卻不一定被允許。切換事件時，注意文件和服務節點，而不是只看顏色。

### U1／2：把要求和做法分開

「私人文件不能被陌生人讀」說明需要維持的結果；「使用某個登入工具」只是可能的做法，還沒有證明它保護哪個結果。

這裡產生的目標句是候選需求，不會改變實際分享政策。改變角色、資源與必要使用時間，對照目標句與節點後果是否一致。

### U1／3：AI 提案需要哪一種依據

能直接描述不可接受結果的提案，仍要確認業務範圍；「全部文件都受法規保護」則需要另外查證，不能由 AI 自行決定。

把提案歸到做法時，繼續問它想避免什麼結果。分類會改變提案與依據的關係，不會自動改寫文件政策。

### U1／4：公開讀取不代表公開修改

分享範圍是允許讀取的條件。條件改變後，要重新檢查原安全要求；不能把所有陌生人讀取都稱為外洩。

保留你的其他設定，只把私人改為公開，先比較讀取，再比較修改。能讀不代表能編輯。

### U2／1：版本、路徑與後果要一起看

套件通知說某些版本有漏洞，不代表每台系統都具有相同攻擊路徑。先確認使用的版本，再確認要求能否碰到弱點，以及成功後會影響什麼。

本圖只比較已設定的路徑，沒有計算真實利用機率。A 的緩解是本轮已查核有效的控制；不要把這個假設擴大到其他入口。

### U2／2：每份來源回答不同問題

CVE 是公開漏洞的識別編號；CVSS 描述技術嚴重度；EPSS 估計未來 30 天被觀察到利用活動的機率；KEV 是已確認實際利用的紀錄。它們都不知道你的完整部署。

Vendor advisory 是供應者通知，local inventory 是本機元件與版本清單。先用兩者確認「我有沒有這個版本」，再接可達路徑與資料後果；不要用單一分數代替這條判斷鏈。

### U2／3：原排序會因條件而改變

B 新增公開入口後，原本未接觸弱點的路徑可能可達；A 有有效緩解後，其本輪路徑的處理理由也會改變。

先看變動的路徑，再比較資料後果與仍缺的證據。沒有對外不等於永遠不可達，還要確認內部工作或其他入口。

### U3／1：身分與允許操作是兩個判斷

Browser 是發出要求的瀏覽器，API 是伺服器受理要求的入口，resource 是被讀取或修改的資料。登入可以確認是 Alice，仍要核對文件是否允許 Alice 做這次操作。

本輪故意把檢查放得太晚：最後顯示拒絕時，資料可能已回傳或修改。開啟讀寫前檢查，觀察 resource 的副作用是否消失，不能只看拒絕回應。

### U3／2：背景工作也有身分與能力

Worker 是替人執行背景工作的程序。它使用 service identity（服務身分）取得特定能力，不應因為來自內網就能操作全部文件。

Scope 是允許的資源與操作範圍。只需要讀指定來源的工作，與可读寫全部資料的工作，失敗後的後果不同。沒有明確允許條件時，預設拒絕仍需保留合法工作路徑。

### U3／3：能阻止副作用的位置才有效

Batch job 是批次處理入口。它繞過原 API 時，原本只放在 API 的檢查不會跟著生效；有登入與有 API 檢查仍不足。

把相同資源政策放在涵蓋所有權威讀寫的位置，才能阻止批次入口的越界修改。本模型的集中資源處只是示例，不表示真實系統必須採同一架構。

### U4／1：資料到了哪個解讀位置

SQL 是資料庫查詢語言，HTML 是網頁結構，path 是檔案位置，process 是執行中的程序。同一資料到了不同元件，可能被解讀成查詢結構、頁面標記、目的地或操作內容。

本圖的結構標記只改合成模型，不執行真正指令。先試一般文字，再試標記，觀察下一站的結構或目的地；資料存過資料庫也不代表下一站可直接相信。

### U4／2：業務驗證與安全建構各管一件事

輸入驗證檢查型別、範圍與業務規則，例如數量必須是正整數；合法自由文字仍可能包含特殊符號。安全建構則要讓這些值保持資料，不能改變解讀器的原結構。

固定 SQL 結構、把值獨立傳入，只保護查詢位置。HTML 需要對應輸出方式，檔案需要限制目的地，程序需要固定操作與獨立參數；依 API 保證查證，不把一種控制當成全部防護。

### U4／3：安全與功能都要成立

Rich text 是需要保留格式的內容，例如粗體或連結。只輸出純文字可以避免活動標記，卻也拿掉功能需要的格式。

本模型的允許內容規則只保留指定結構。比較純文字與允許規則時，同時看解讀器是否受外部值改變、畫面是否完成格式需求；本課不教完整富文字處理實作。

### U5／1：起點已失守，還有哪些條件限制它

本章接前一章的允許規則，先假設 API 或 Worker 已被控制，不再估算能否攻破它。Credential（憑證）是用來取得身分或能力的值，route 是可建立的連線路徑。

攻擊者繼承起點能用的憑證與連線，但下游自己的權限仍可能阻擋操作。看「碰得到」和「能做什麼」兩件事，而不是看到連線就認定全部失守。

### U5／2：網路可達不等於有修改權限

分段限制連線，最小權限限制允許的操作。兩者在不同邊界生效，不能互相取代；共用高權限憑證可能把多個元件連成同一組能力。

例如資料庫仍可達，但身分只讀時，讀取仍可能發生，修改或刪除能力才被縮小。比較節點上的具體操作，別只數被阻擋的線。

### U5／3：合法工作也需要路徑

背景工作現在必須寫出一個縮圖。完全封鎖儲存空間雖可阻擋這條路徑，也讓工作無法完成。

改為只讀寫指定物件，再觀察剩餘能力與正常工作結果。影響範圍是明示假設下的資源與操作，不是安全分數。

### U6／1：誰還能取得解密能力

靜態加密保護儲存層；傳輸中加密保護傳輸層。本圖先比較磁碟被拿走與執行中應用被控制：後者如果能取得明文或呼叫解密，資料仍可能被讀取。

Key 是解密需要的金鑰。把金鑰放別處，只有在失守身分也不能讀它或使用解密能力時才擋住這條路徑。少保存非必要敏感欄位則直接减少本輪可暴露資料。

### U6／2：刪原文、換新值、撤銷舊值

Token 是可取得特定能力的憑證；consumer 是實際使用它的服務或工作。公開副本已被複製時，刪除原文不會使副本失效。

建立替代值是輪替的一部分，撤銷才讓舊值失效；consumer 還必須切換到新值。縮小 token 範圍也只縮小能力，不自動撤銷它。

### U6／3：軟體交付不是只看套件名稱

Dependency 是依賴套件，CI 是自動建置／檢查流程，artifact 是建置後可部署的產物。誰能替換其中一段，可能改變最後執行內容。

Provenance（來源證據）幫你核對產物從哪裡來；來源吻合仍不能證明程式無漏洞。套件通知也需要核對版本與實際使用路徑，不能直接當本部署可被利用的證明。

### U6／4：舊值失效與工作可用要一起驗證

Consumer 沒切換時就撤銷舊 token，可能阻止洩漏副本，也同時中斷合法工作。這是兩個要分開觀察的結果。

試著建立替代值、更新 consumer，再撤銷舊值；比較外洩副本是否仍可用與合法工作是否能繼續。本圖不模擬真實 provider 的切換時間。

### U7／1：先說清想證明的主張

Claim 是想驗證的主張，例如 Alice 不能改 Bob 的文件。SAST 分析程式碼線索；SCA 檢查依賴組成與版本；secret scan 找疑似秘密字串；行為測試檢查指定操作與副作用。

工具 finding（發現）是符合規則的結果，需要調查。這個畫面是固定合成規則，不執行真實 Semgrep；啟用不同來源只改可見證據，不會自動修正缺陷。

### U7／2：修正後，仍要看未涵蓋的地方

Query 是查詢內容；fixture 是示範測試資料；sink 是資料進入敏感操作的位置。相似字串建構不代表兩者有相同風險，要追來源與用途。

修正 query 後，對照 match 是否消失，再看 fixture 的適用性與重複退款仍未涵蓋的業務規則。誤報是標到非目標問題；漏報是目標問題存在但沒找到。沒有 finding 不能擴大成全部安全。

### U7／3：紀錄能連起事件，警示仍需調查

Log 是發生事情留下的紀錄，alert 是規則指出需要調查的訊號。時間、入口、身分與操作欄位幫你知道發生什麼；interaction ID 用來關聯同一操作跨服務的紀錄。

加上關聯資訊後觀察可重建的範圍，不要猜完整故事。密碼、token 與不必要敏感內容不應直接寫入 log；紀錄本身也需要保護。

### U7／4：綠燈只屬於受測條件

負向測試驗證禁止行為被拒絕且資料沒變；回歸測試讓已修正行為在後續變更仍成立。這裡的 API 測試只驗證一条入口。

新增背景工作後，API 綠燈仍可能成立，卻沒有驗證新的工作入口。Coverage（涵蓋範圍）是證據實際查過的路徑與條件，不能因工具一致就自動擴大。

### U8／1：有線索，仍要保留未知

先接 U7 的事件紀錄。身分使用紀錄、資源紀錄與可關聯時間，各自補上事件的一部分；警示不是完整故事。

先列出受影響身分、資源與時間哪些有證據，再選限制持續傷害的動作。不需要等所有未知都解開，但每個動作要說清依據與可能副作用。

### U8／2：停止新部署與停止既有程序不同

撤銷部署憑證可阻止它繼續發布，但已執行的未知程序可能仍有資料權限。隔離服務可限制這條路徑，卻會影響合法使用。

Containment（限制影響）是在止住持續或擴大的傷害，還沒有證明資料與產物可信。比較撤銷、隔離與縮小資料能力各改了哪條路徑。

### U8／3：可信恢復需要多份證據

Rollback 是把程式換回舊版本，restore 是還原資料；兩者都不會自動撤銷外洩憑證。重新部署已核對來源的產物，也需核對下游秘密與資料狀態。

本圖分開列出產物、憑證、資料與可用性。還原後另驗完整性與時間點，確認持續路徑受控，再請求恢復；本輪 gate 只支持畫面列出的假設。

### U8／4：讓同類問題可再次查核

回歸測試檢查已修正行為能否維持，偵測規則觀察運作訊號，權限修訂減少能力，threat model 則記錄系統與威脅假設。

四者作用不同。回到本次已知原因與證據，說明哪項改變能阻止或發現同類路徑；新增一個測試不等於全部事件已涵蓋。

### U8／5：備份還原只是其中一步

備份存在不代表還原結果完整或足夠新；還原也不會終止仍有效的憑證或執行中程序。

只打開 restore 時，檢查哪些可信條件仍缺。逐項補上並再次觀察可用性與事件路徑，保留本輪未驗證的未知。

### Final Transfer refinement

原先選 domain 只改名稱，不足以支持遷移目標。保留合成 teaching 系統與 evidence，載入兩個不同需求情境：案件系統需要私人資料不可被未允許修改；自動發文需要公開内容可讀、發布能力僅限指定工作，但未知部署內容仍需查核。需求與 sharing／worker／產物狀態一起改變，不提示應套用哪章。明示切換會載入情境設定、不是實際專案資料。Transfer 不提供答案卡；要求 learner 指出后果、證據與未知。此修訂補足既有 transfer outcome，沒有增加新技術主題。
